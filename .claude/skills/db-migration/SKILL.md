# Миграции без доступа к базе

## Почему так

Песочница разработки выпускает наружу только HTTPS. Порт 5432 закрыт, поэтому
`prisma migrate dev` (которая обычно и пишет SQL за тебя) просто не достучится
до Neon. Зато сборка на Vercel до базы достаёт и выполняет `prisma migrate deploy`.

Отсюда рабочая схема: **SQL пишем руками, применяет его деплой.**

## Порядок

### 1. Поправить `prisma/schema.prisma`

Обычные правила проекта: без `enum` (роль и тип работы — строки со схемой
`zod` как источником правды), комментарии `///` над полями объясняют смысл,
а не повторяют название.

### 2. Написать SQL руками

Каталог: `prisma/migrations/<номер>_<короткое_имя>/migration.sql`.
Номера идут подряд: `0_init`, `1_logins_quarters_multigrade`,
`2_security_hardening`, `3_grade_types_absences`, `4_phase2`,
`5_equal_weights`, `6_lesson_homework_plan`. Следующая — `7_*`.

Порядок применения — **лексикографический по имени каталога**. Пока номеров
меньше десяти, всё сходится с числовым порядком; начиная с `10_` сортировка
поставит его перед `2_`. Если дойдёшь до десятой миграции, переходи на
двузначные имена с ведущим нулём для новых.

Начинай файл с комментария: что меняется и зачем. Через полгода это
единственное объяснение, почему поле называется именно так.

### 3. Проверить, что не сломаешь существующее

* `DROP INDEX` / `DROP CONSTRAINT` — сверь имя с тем, что реально создали
  предыдущие миграции (`grep -rn "имя" prisma/migrations/`). Prisma называет
  уникальные индексы `Таблица_поле1_поле2_key`, обычные — `..._idx`.
  Промахнёшься именем — миграция упадёт на боевой базе, и деплой встанет.
* Prisma не умеет описывать **частичные** индексы. Если нужен такой (у нас
  так сделана уникальность живых уроков:
  `CREATE UNIQUE INDEX ... ON "Lesson"("subjectId","date") WHERE "deletedAt" IS NULL`),
  индекс живёт только в SQL, а в `schema.prisma` остаётся обычный `@@index`
  с комментарием, объясняющим расхождение.
* Добавление nullable-колонки без `DEFAULT` — дешёвая операция, таблица не
  переписывается. Колонка `NOT NULL DEFAULT` на большой таблице — уже нет.

### 4. Проверить без базы

```bash
npx prisma validate     # схема синтаксически верна
npx prisma generate     # клиент пересобран под новые поля
npm run typecheck
```

Соединения ни одна из этих команд не требует.

### 5. Данные приводим в порядок в той же миграции

Если правка меняет смысл уже накопленных данных — допиши `UPDATE` прямо в
миграцию. Пример из проекта: когда убрали удвоение веса контрольной,
миграция `5_equal_weights` выполнила
`UPDATE "Grade" SET "weight" = 1 WHERE "weight" <> 1;`, иначе старые оценки
считались бы по прежним правилам, а новые — по новым.

**Окно деплоя.** Между применением миграции и переключением трафика на новый
код старая версия ещё работает и может записать данные по старым правилам.
Поэтому такие `UPDATE` стоит продублировать в следующей миграции как
страховку — так сделано в `6_lesson_homework_plan`. Стоит одну строку,
закрывает целый класс «почему у одной оценки другой вес».

## Чего не делать

* `prisma migrate dev`, `prisma db push`, `prisma studio` — им нужна живая
  база, здесь они только потратят время на таймаут.
* Не редактируй уже применённую миграцию. Prisma хранит контрольную сумму
  каждой; изменение файла задним числом ломает `migrate deploy` на проде
  сообщением о несовпадении. Нужна правка — новая миграция.
* Не удаляй колонку в той же миграции, где перестал её использовать. Сначала
  выкатывается код без обращений к ней, потом отдельной миграцией — удаление.
  Иначе старый код в окне деплоя обратится к несуществующей колонке.
