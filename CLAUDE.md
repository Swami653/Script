## 1. Три правила, которые нельзя нарушать

### 1.1. Оценки — строго 10-балльные

Оценка — **целое число от 1 до 10**. Ни дробей, ни нуля, ни 11, ни «н/а», ни строк.

- Единственный источник правды: `gradeValueSchema` в `src/lib/grades.ts`.
- Любая запись оценки на сервере обязана пройти через эту схему. Не пиши собственных
  проверок вида `if (value > 0 && value < 11)` — используй схему.
- Валидация на клиенте не считается защитой. Клиент может прислать что угодно.

### 1.2. Учебный год — ровно 4 четверти

Четверть — целое число **1, 2, 3 или 4** (`quarterSchema`, константа `QUARTERS`).

Расчёты (реализованы в `src/lib/grades.ts`, не дублируй их):

| Величина | Как считается | Округление |
|---|---|---|
| Средний балл за четверть | среднее арифметическое оценок четверти | до сотых (`7.45`) |
| Годовая оценка по предмету | среднее средних баллов **непустых** четвертей | до целого 1–10, `0.5` вверх |

Четверть без оценок в расчёте годовой не участвует (иначе один пропущенный
период занижал бы итог). Нет оценок вообще → `null`, в интерфейсе `—`.

### 1.3. Права проверяются на СЕРВЕРЕ

Каждое Server Action и каждый Route Handler начинается с проверки роли:

```ts
"use server";
export async function someAction(input: unknown) {
  try {
    const user = await requireRole(GRADE_EDITOR_ROLES); // 403, если роль не подходит
    // ...
  } catch (error) {
    return actionError(error); // { ok: false, status: 403, error: "…" }
  }
}
```

- `requireUser()` → 401, если пользователь не авторизован.
- `requireRole([...])` → 403, если роль не входит в список.
- `requirePageUser()` / `requirePageRole([...])` — версии для страниц: вместо ошибки
  редирект на `/login` или в раздел своей роли.

**Ученик не может выставить, изменить или удалить оценку ни при каких условиях.**
Скрытая кнопка — это не защита. Middleware — это не защита. Защита — `requireRole`
внутри действия.

Формат ответа различается по слою, и это нормально:

| Слой | Как выглядит отказ |
|---|---|
| Server Action | HTTP 200 + `{ ok: false, status: 403, error: "…" }` (payload RSC) |
| Route Handler | настоящий HTTP 403 + `{ "error": "…" }` |
| Страница | редирект на свой раздел |

## 2. Роли

| Роль | Может | Раздел |
|---|---|---|
| `ADMIN` | всё управление пользователями, массовый импорт, сброс паролей, + права учителя | `/admin` |
| `TEACHER` | предметы, уроки, оценки, карточки учеников | `/journal` |
| `STUDENT` | только собственный дневник, только чтение | `/student` |

Роли объявлены в `src/lib/roles.ts` (`ROLES`, `Role`, `GRADE_EDITOR_ROLES`).
**SQLite не поддерживает `enum` в Prisma**, поэтому в базе роль — строка,
а типобезопасность даёт `asRole()` / `isRole()`. Не добавляй `enum` в схему.

## 4. Модель данных

```
User  1─┬─* Grade (как ученик,  relation "StudentGrades")
        └─* Grade (как учитель, relation "TeacherGrades")
Subject 1─* Lesson 1─* Grade
```

- `Lesson` — это **столбец журнала**: предмет + дата + четверть (+ тема).
  Уникальность: `@@unique([subjectId, date])` — один урок на дату по предмету.
- `Grade` — ячейка. Уникальность: `@@unique([studentId, lessonId])` — у ученика
  не может быть двух оценок за один урок.
- `Grade.subjectId` и `Grade.quarter` **денормализованы** ради быстрых агрегатов.
  **Инвариант:** они всегда равны полям своего урока. Заполняй их только значениями
  из `lesson`, никогда из пользовательского ввода (см. `setGradeAction`).

Даты уроков хранятся как **полночь UTC** (`parseDateInputValue`) и форматируются
UTC-методами (`formatDateShort`). Не переходи на локальные `getDate()` — дата поедет.

## 6. Как добавить новое действие с данными

1. Файл в `src/lib/actions/` с `"use server"` в первой строке.
2. Первая строка тела: `await requireRole([...])` внутри `try`.
3. Валидация входа схемой `zod` — **всех** полей, включая id.
4. Работа с БД через `prisma`.
5. `revalidatePath(...)` для затронутых разделов.
6. `catch (error) { return actionError(error); }` — 401/403/400/500 разложатся сами.
7. На клиенте: `if (!result.ok) show("error", `${result.status}: ${result.error}`)`.

Никогда не возвращай клиенту `password`, даже хеш.

## 8. База данных и развёртывание

Рабочая СУБД — **PostgreSQL** (Neon). В схеме два источника:

- `url = env("DATABASE_URL")` — пулированное соединение (pgbouncer), его использует
  приложение. Параметры `pgbouncer=true&connection_limit=1` обязательны: без них
  serverless-функции исчерпают лимит соединений.
- `directUrl = env("DIRECT_URL")` — прямое соединение, нужно только миграциям.

Схема меняется **только миграциями**: `npx prisma migrate dev --name <что-меняем>`
локально, а на Vercel их применяет скрипт `vercel-build`
(`prisma migrate deploy` + идемпотентный `prisma/seed-if-empty.ts`).
Не вызывай `prisma db push` на боевой базе — потеряешь историю изменений.

Демо-данные (`src/lib/demo-data.ts`) заливаются только в пустую базу.
`npm run db:seed` очищает таблицы — на бою его запускать нельзя.

## 9. Чего не делать

- Не проверять роль только в middleware или только на клиенте.
- Не заводить оценки вне диапазона 1–10 и «пятую четверть».
- Не дублировать формулы средних баллов — они в `src/lib/grades.ts`.
- Не хранить пароли иначе как `bcrypt.hash(password, 10)`.
- Не коммитить `.env` и `prisma/dev.db` (уже в `.gitignore`).
- Не добавлять `enum` в схему Prisma (SQLite их не поддерживает).
